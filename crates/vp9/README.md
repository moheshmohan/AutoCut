# filmcraft-vp9

Clean-room, pure-Rust (no `unsafe`) VP9 decoder, implemented from the public *VP9 Bitstream &
Decoding Process Specification* v0.6 (WebM project). It is an L0 crate: it depends only on
`filmcraft-bitstream`, `thiserror`, and optionally `rayon` (default feature `threads`), and builds
for `wasm32-unknown-unknown` with and without `threads`.

The constant tables (probability defaults, scans, coefficient bands, quantizer lookups, Pareto
table, interpolation filters, `mv_ref_blocks`...) were extracted from the specification text by
[`tools/extract_tables.py`](tools/extract_tables.py) into `src/spec_tables.rs`. The 1D inverse
DCT / ADST butterflies are generated by [`tools/gen_transforms.py`](tools/gen_transforms.py),
which symbolically executes the step lists of spec section 8.7.1 into `src/transform_gen.rs`.
No code was taken or ported from libvpx, FFmpeg or any other decoder; ffmpeg (with libvpx-vp9)
is used only as an external fixture generator and test oracle.

## API

```rust
use filmcraft_vp9::{Decoder, Plane};

let mut dec = Decoder::new(); // or Decoder::with_threads(n)
for (pts, chunk) in chunks {  // one IVF / WebM block / MP4 sample each (frame or superframe)
    for pic in dec.decode(chunk, pts)? {
        // pic.width / pic.height (frame size), pic.render_width / render_height (render_size),
        // pic.bit_depth, pic.subsampling_x / subsampling_y, pic.chroma_width / chroma_height,
        // pic.y / pic.u / pic.v: Plane::U8(Vec<u8>) for 8-bit, Plane::U16(Vec<u16>) above,
        // pic.y_stride / pic.uv_stride, pic.pts, pic.key, pic.intra_only,
        // pic.color { color_space (0..7 as coded), full_range }
    }
}
let rest = dec.flush(); // pictures still in flight (frame threads)
// dec.set_draft(true): draft mode (playback at reduced resolution only), dec.threads()
dec.reset(); // forget references / contexts (seek), keeps the thread pool
let stats = dec.stats(); // what the stream exercised (frame kinds, tiles, compound, scaling...)

// Random access points: does a container sample start with a key frame (and its parameters)?
let key: bool = filmcraft_vp9::is_keyframe(chunk);
let info: Option<filmcraft_vp9::KeyframeInfo> = filmcraft_vp9::keyframe_info(chunk);
```

`filmcraft-codecs` wires the decoder into Matroska / WebM (`V_VP9`, profile / bit depth from
`CodecPrivate`, colour from `Colour`) and MP4 (`vp09` + `vpcC`) import; its GOP cache asks
`is_keyframe` before starting a decode at a container sync sample, so wrongly flagged samples
(e.g. an MP4 without `stss`) still seek correctly.

A superframe produces every shown frame it contains (normally one); hidden frames produce none.
With frame threads (`Decoder::new()`, or `with_threads(n)` with n > 1) a picture can come out of
a later `decode` call or `flush` (each carries the `pts` of the chunk that showed it);
`with_threads(1)` returns every picture from the call that completes it.

### Architecture

The calling thread parses the uncompressed and compressed headers and manages the eight reference
slots, the four probability contexts, segmentation map and previous-frame motion vectors. Each tile
column is decoded by one `TileDecoder` into a private strip of samples and mode info (tile rows of
a column are decoded in order: they share above contexts); the calling thread decodes columns
itself and helpers on the rayon pool take the others, so no column waits for a helper to wake up.
Each frame's **post stage** runs on a thread of its own from the start of the frame (`Pipe`): as
soon as a column has decoded a superblock row it hands the row's samples and loop filter mode info
over, and once every column has, the post thread assembles the row ("band"), loop filters it
superblock by superblock (rows in order, so the result is the specification's), publishes the band
above it once that can no longer change (`OnceLock` per band; the 16-wide filter of row r reads 8
and changes 7 rows of row r - 1, which travel in 8 padding rows on top of each band) and copies it
into the output picture. A frame is thus mostly filtered by the time its last tile row is decoded.
Counts are then merged for backward adaptation, the mode info is assembled (the next frame reads
it for motion vector prediction and segment ids) and the frame goes into the reference slots at
once. Motion compensation of later frames reads reference rows through `Frame::row` /
`Frame::span`, which wait for exactly the bands a block reaches. Probability adaptation needs only
the counts, so even backward-adaptive streams start the next frame before the loop filter is done;
frame-parallel / error-resilient streams (no backward adaptation) never wait at all. With one
thread the rows are filtered after the frame's tiles (each band built, filtered and copied out in
one go, for locality). Results never depend on scheduling: the conformance suite decodes every
fixture with 1, 3 and all threads. Samples are `u16` internally for every bit depth.

Draft mode (`Decoder::set_draft(true)`; FilmCraft enables it with Settings ▸ Playback ▸ Draft
decoding while the Program monitor plays at 1/2 or 1/4): frames with `refresh_frame_flags` 0 —
no reference slot receives them, so nothing predicts from their samples — skip the loop filter
and are flagged `Picture::draft`. The loop filter changes neither mode info, segmentation map nor
probabilities, so every other frame is unchanged. Such frames occur in temporally layered streams
(e.g. libvpx `-ts-parameters`); single-layer realtime streams refresh LAST on every frame.

Modules: `header` (6.2 / 6.3, superframes), `boolcoder` (9.2), `probs` (frame contexts, counts,
8.4), `tile` (partition / mode info / MV prediction), `tile::recon` (residual, tokens, intra /
inter prediction calls, reconstruction), `intra`, `inter`, `transform`, `loopfilter`, `frame`
(banded frames, pools), `decoder` (scheduling, post stage).

## Memory

A frame is refused (`Error::Invalid`, before anything is allocated for it) when a side is over
16384, when its luma plane has more than `Decoder::set_max_picture_luma_samples` samples
(`MAX_LUMA_SAMPLES` = 2^26, 8192x8192, by default), or when what the decoder would hold at that
size does not fit `Decoder::set_memory_budget`. The count follows the decoder's threading: the
eight reference slots, the frames whose post stage still runs (at most `(threads / 3).clamp(2, 6)`
with frame threads, the new frame's included; one without), and the output pictures those post
stages build, the ones waiting in the output queue (at most `(threads / 2).clamp(2, 6)`) and up to
two more shown by the same chunk; so at most 14 frames and 14 pictures, whatever the thread count.
Frames count their real sample bands (two bytes a sample on the 64-sample grid, with the scratch
rows of each band), pictures their planes (one byte a sample at 8 bits, two above).

`DECODE_MEMORY_BUDGET` is 12 GiB on 64-bit targets: more than the decoder can hold for any frame
the size limits admit, in every profile, at any thread count (the most is about 12.1 GB, 4:4:4 at
12 bits and 2^26 luma samples; a level 6.2 frame at most about 6.5 GB; 8K UHD 4:4:4 12-bit about
5.9 GB at 18 threads or more), so the default refuses nothing those limits let through and binds
once a caller raises them. On 32-bit targets it is 1 GiB (one thread: 9 frames and 3 pictures):
8-bit 4:2:0 fits up to about 29 million luma samples, so 8K UHD (1.2 GB) is refused there. A caller
past 8K raises the luma limit and the budget together.

## Tests

`cargo test --release -p filmcraft-vp9`. Fixtures are generated on first use into
`target/fixtures/vp9/` with ffmpeg + libvpx-vp9 (tests print a message and skip when ffmpeg or
libvpx is unavailable). Every frame is compared sample-exactly with `ffmpeg -c:v vp9 -f rawvideo`
output with 1 thread, 3 threads (frame threading with a small pool) and every core; the first
mismatch reports frame, plane, position and superblock. No picture may be flagged draft without
draft mode.

- Unit tests: boolean decoder against a literal model of 9.2, tables / trees, inverse DCT / ADST
  against floating-point bases, DC-only shortcut vs. full transform, the column-parallel 2D
  transform against the per-column formulation on random blocks of every size and type, scaled
  MC path vs. unscaled (through a banded reference frame), superframe index, `inv_remap_prob`,
  probability merging.
- Draft mode (`draft_mode_changes_only_flagged_non_reference_frames`): on a two-layer temporal
  scalability stream, single- and frame-threaded, every unflagged frame is bit-exact and only
  flagged frames differ.
- Conformance (`tests/conformance.rs`): the fixture matrix below plus a stream concatenating two
  sizes. `compare_detects_mismatch` guards the harness. `coverage_report` (ignored) prints the
  decoder statistics for each fixture.
- Synthetic (`tests/synthetic.rs`): headers of libvpx output are rewritten to produce what ffmpeg's
  libvpx wrapper cannot: inter frames of a stream encoded at another size spliced after a 352x288
  key frame with explicit frame sizes, i.e. **scaled reference prediction** (downscale 256x208,
  upscale 480x400, odd 301x199; a same-size splice is the control); a key frame rewritten as a
  hidden **intra-only frame** (reset_frame_context 3 / 2 / 0, various refresh masks) shown with
  **show_existing_frame**; show_existing_frame of every slot, also inside a superframe.
- Robustness (`tests/robustness.rs`): bit flips, byte replacement and truncation of real streams,
  truncated frames, random data and oversized frames never panic (debug and release) or hang,
  single- and multi-threaded.
- Superframe length regressions (`header::tests::hostile_lengths_*`, #2801) run without media
  fixtures on native and 32-bit WASI targets. Oversized frame lengths cannot wrap an offset;
  truncated indexes retain the existing remaining-payload fallback. See
  [32-bit parser tests](../../docs/testing.md#32-bit-parser-regressions).

## Performance

`cargo test --release -p filmcraft-vp9 --test perf -- --ignored --nocapture` (bit-exactness is
verified first), or `VP9_THREADS=n VP9_LOOPS=k cargo run --release -p filmcraft-vp9 --example
vp9dec -- in.ivf` (decodes the file k times and prints the statistics; `VP9_DRAFT=1` for draft
mode).

M4.10 (2026-10-03), Apple M4 Pro (14 cores) shared with other builds (load average 190-320), so
the figures are CPU cycles per frame counted by the kernel (`/usr/bin/time -l`, all threads
summed; mean of two interleaved base / after rounds) — wall clock only within a round. Fixtures:
the `cargo xtask bench` decode clips (testsrc2 + grain, libvpx realtime speed 8, CRF 32; 1080p
4 tile columns, 2160p 8 tile columns, frame-parallel mode), bit-exact with ffmpeg.

| stream | threads | Mcycles / frame before | after | wall ms / frame before → after (same load) |
|---|---|---|---|---|
| 1080p (120 frames) | 1 | 68.0 | **52.0** (−24 %) | |
| 1080p | 14 | 100.7 | **57.9** (−43 %) | 95, 82 → 18, 17 |
| 2160p (72 frames) | 1 | 273.6 | **205.8** (−25 %) | |
| 2160p | 14 | 391.7 | **219.2** (−44 %) | 146, 118 → 38, 36 |

Before M4.10 the frame-level work was serial (tile columns of one frame, then a loop-filter
wavefront, then assembly and output conversion), so 14 threads spent 40-50 % more cycles than one
thread (spinning between short parallel phases) and a 4K frame still took ~120 ms of wall time
at this load; now the post stage overlaps the next frames and 4K decodes at ~27 fps on the
loaded machine. What changed:

- **Frame threading** (see Architecture).
- **Loop filter** (was ~50 % of single-threaded time): the lane masks were `bool`s with
  `clamp` and branchy selects, which kept the "vectorised" group filter scalar; masks are now
  0 / -1 integers with bitwise selects and min / max clipping, so it compiles to NEON.
- **Inverse transforms**: the column pass runs the generated butterflies
  (`transform_gen::cols4` / `cols8`) on 4 / 8 columns at once.
- **Motion compensation**: 8-bit sub-pixel filters accumulate in 16-bit lanes (8 per vector
  instead of 4): every sum of the VP9 filters plus rounding lies in [-13706, 46474], so the sum
  modulo 2^16 identifies it (negative sums clip to 0).
- Bool decoder: branch-free update.

Single-threaded 4K time now splits into coefficient tokens (bool decoding) ~27 %, loop filter
~25 % (two thirds of it the vertical-edge transposes and per-group decisions), motion
compensation ~15 %, inverse transforms ~8 %, intra prediction ~6 %.

### High bit depth (2026-10-21)

Phone footage from Google Photos is mostly 1080p VP9 profile 2 (10-bit 4:2:0, 60 fps, 4 tile
columns, backward adaptation, compound prediction in 80 % of the frames), where motion
compensation was 46-50 % of single-threaded time: smooth content means large blocks with
sub-sample vectors, i.e. the 2D 8-tap filter on 64x64 and 32x32 blocks. Same machine, shared
with other lanes' builds (load average 20-50), 300 frames of three of the owner's clips (not in
the repository), median of 3 interleaved runs. Instructions and cycles are counted by the kernel
(`/usr/bin/time -l`, all threads); instructions do not depend on the load, wall-clock fps does.

| clip (1080p 10-bit) | threads | M instructions / frame | M cycles / frame | fps (median, same load) |
|---|---|---|---|---|
| IMG_9626 | 1 | 211.0 → **127.6** (−40 %) | 50.9 → **39.3** (−23 %) | 56.2 → **69.5** |
| IMG_9626 | 14 | 219.0 → **132.0** | 69.6 → **54.5** | 94.4 → **159.3** (1.7×) |
| IMG_4820 | 1 | 221.7 → **136.0** (−39 %) | 51.6 → **39.3** (−24 %) | 53.4 → **64.2** |
| IMG_4820 | 14 | 230.0 → **140.7** | 70.8 → **54.3** | 90.2 → **159.6** (1.8×) |
| IMG_8489 (portrait) | 1 | 223.4 → **146.2** (−35 %) | 54.6 → **43.4** (−21 %) | 50.4 → **63.7** |
| IMG_8489 (portrait) | 14 | 230.6 → **149.9** | 72.4 → **56.5** | 78.0 → **152.0** (1.9×) |

With the machine quieter (load ~20) IMG_9626 decodes at 291 → 430 fps with 14 threads. The
headless playback benchmark (`cargo xtask bench-playback`, GPU path, the `h264-1080` scenario
with IMG_9626 as its clip: a 23.976 fps 1080p sequence, 2.5 decoded samples per shown frame)
needs 63 → 41 ms of CPU per shown frame (1.5 → 1.0 cores) and its p95 frame latency drops from
59-271 ms to 16-59 ms; with the clip in a 2160p sequence (`vp9-2160`), 58-61 → 39-40 ms.

What changed:

- **Motion compensation kernels.** High bit depth sums multiply sign-extended 16-bit samples
  and taps into 32-bit lanes (widening multiply-accumulates, 8 products per instruction pair),
  narrowing with a saturating shift; 16-bit sums stay for 8-bit (the range proofs are in
  `inter.rs`: 10 / 12-bit sums span about 2^20). Rows are filtered whole (taps outer, samples
  inner), the form the compiler vectorises without spilling the sums, and the sums start from
  the first tap (a constant splat became a `memset_pattern16` call per row on Darwin). A 10-bit
  2D filter went from 1.45 to 0.52 ns per sample (64x64) and from 3.9 to 1.6 (8x8).
- **No copies around prediction.** Source rows are read in place from the reference bands also
  when a block's window crosses a band boundary (they were copied into a window first), the
  window copy for blocks past the left / right edge is a run copy with edge fills, and the
  first prediction is written straight into the frame (compound blocks average the second one
  into it).
- **Loop filter pipelined with the tiles** (see Architecture): the post thread filters each
  superblock row as soon as every tile column has decoded it. The next frame's columns used to
  wait for reference rows 30 % of the time; the old wavefront woke a thread per superblock
  (rows ran ~250 µs apart instead of ~10 µs) and its blocked helpers held pool threads the next
  frame's columns needed.
- **Tile columns start at once**: the calling thread decodes columns itself and pool helpers
  take the rest.
- **Loop filter decisions**: each superblock resolves the mode info of its 8x8 cells once per
  plane type instead of once per 8-sample group, edge and pass (87 % of those lookups found no
  edge).

Single-threaded time now splits into motion compensation ~45 % (within about 1.5x of the
multiply-accumulate throughput of this formulation), loop filter ~19 % (vertical-edge
transposes, which safe Rust cannot express as vector permutes, and per-group decisions),
coefficient tokens ~9 %, band and picture copies ~5 %, inverse transforms ~5 % (the 10-bit
column pass is scalar 64-bit).

## Known gaps

- A frame's tile decoding is still a barrier: the next frame starts once every tile column of
  the current one is done (its loop filter runs alongside), so streams with a single tile column
  decode their tiles on one thread at a time, and a 1080p frame (4 tile columns at most) waits
  for its slowest column. Splitting entropy decoding from reconstruction would let the next
  frame's parsing start while the current one is reconstructed. The loop filter of one frame
  runs on one thread (on a quiet machine it takes about as long per frame as the tile phase).
- Scaled references combined with compound prediction are not covered by a fixture (both are
  verified separately; libvpx through ffmpeg cannot change size mid-stream and the synthetic
  splice cannot keep the compound streams' probability contexts intact).
- Frames larger than 16384x16384 are rejected (`Error::Invalid`) to bound memory (see Memory).
- Damaged streams are decoded as far as the data allows (the boolean decoder reads zeros past the
  end, as specified); there is no concealment beyond that, and inter frames whose reference slots
  are empty return `Error::MissingReference`.
